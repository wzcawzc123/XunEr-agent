## 一、任务清单（Task Plan）

### 解决什么问题

**真机数据**：最长的会话 6,320 条消息、压缩 7 次。上下文压缩会把此前的
`todo_write` 回执摘要掉，模型随即失去「我在第几步」的记忆 —— 表现为反复重做、
或用"已完成/待办"的口头描述代替真正的进度跟踪。

### 设计决策

| 决策 | 选择 | 为什么不选另一条路 |
|---|---|---|
| **存储** | 独立表 `conversation_todos` | 放进 context checkpoint 会被压缩重写，而清单的价值恰恰是"压缩后还在" |
| **写入语义** | 全量覆盖（省略即删除） | 单线程 agent 无并发，增量更新只会多出三类状态不一致 |
| **工具数量** | 1 个 `todo_write` | Claude Code 用 Create/Get/Update/List 四件套，那是因为它支持并发子代理 |
| **状态值** | pending/in_progress/completed/cancelled | 不做 `deleted` 状态：省略即删除，少一个状态少一类非法转换 |
| **双形态** | `subject` + `activeForm` | UI 列表显示名词、进行中显示"正在…"，模型直接给比字符串拼接自然 |

### 与压缩的集成（关键）

```
压缩发生时：
  ① 摘要生成（原逻辑不动）
  ② todos 表原样保留（不参与压缩）
  ③ 摘要正文追加一行：[当前任务清单] 2/7 完成 · 进行中：修复判据
```

**传递链用回调而非硬依赖**：`AgentContextSession` / `AgentLoop` / `complete()`
各加一个 `planOverview: () -> String? = { null }`，由运行时层注入 ——
model 层不必知道数据库长什么样。

### 已知缺口

- 模型是否**主动**使用 `todo_write` 未验证（需要真机跑一次多步任务）
- 没有"计划-确认-执行"的闸门（现在是边做边更新清单）

## 二、成本面板（Cost Panel）

### 解决什么问题

用户在花钱，但不知道花在哪。更具体地说：**不知道缓存有没有起作用**。

### 真机数据（改造前）

```
4,494 轮 / 输入 17.1 亿 tokens / 缓存命中 96% / 可计费输入 5,230 万
```

**96% 命中意味着**：如果缓存失效，成本翻 25 倍。

### 设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| **聚合位置** | SQL（`SUM`/`COUNT`） | 大会话上万条消息，只为几个总数把整表读进内存不值得 |
| **类型** | 全部 `Long` | 单会话输入已达十亿级，`Int` 会溢出 |
| **脏数据** | `coerceAtLeast(0)` + 命中率钳到 1.0 | 某些兼容端点会重复累加 cached，必须防负数和 >100% |
| **展示** | 只给三个指标（总量/命中率/可计费） | 参考 llm-usage-dashboard / MLflow / Braintrust，但**不堆图表** |
| **单位** | 亿 / 万 | 17 亿级的裸数字既难读又会把行挤到换行 |

### 分层

```
AgentCostSummary   纯数据 + 计算（7 个单测）
AgentCostRepository Room 投影 → 领域模型（唯一转换点）
AgentUsageScreen   只读展示（进页面读一次，不轮询）
```

## 三、记忆分层（Memory Layering）

### 发现的真问题

```
MEMORY.md 149,623 字符
核心记忆章节 28,575 / 32,000 = 89%   ← 快满了
其中约 17,000 字符是"已结项的项目档案"
```

**后果**：再涨 3,400 字符就触发 `truncateCore` 按行截断 ——
新加的规则会**被静默丢掉**，而且没人知道。

### 做了什么

| 层 | 动作 |
|---|---|
| **可观测** | `memory_get` 返回 `core_usage`（used/budget/percent/truncated/sections/lines）|
| **归档** | 17 个结项项目移到文末 `# 归档`（23,257 字符），核心 89% → **17%** |
| **归档标识** | 读到归档内容时返回 `archived: true`，避免模型把历史结论当现状 |

### 归档判定为什么用"最后一次 `# 归档`"

归档正文里可能提到 `# 归档` 字样；按第一次出现会把核心区误判成归档。
因此取**最后一行**作为分界线（`isArchivedRead`，7 个边界测试覆盖）。

### 数据安全

- 备份：`MEMORY.md.bak_20261018_153634`（242,552 字节）
- 归档 = **移动**，不是删除；内容一字未改，全部可 `memory_get` 检索
- 验证：122/122 标题完整，丢失 0
