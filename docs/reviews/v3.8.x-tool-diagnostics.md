# v3.8.x 终端报错诊断审查（2026-10-07）

承接上游 3.2.0 合并（v3.8.0）后的全量审查。起因：合并后终端类失败提示
**无法区分「设计限制」与「真实故障」**，会话里只能靠猜。

## 一、范围与方法

- **三源集合比对**：能力目录（模型可见的 schema）／要求表（`AgentToolRequirements`）／
  执行分发（`AgentLocalTools` 的 when 分支）——两两求差，找"能执行但模型看不到"与
  "模型能调但执行崩"的名字。
- **出身判定**：用 `git log --diff-filter=A` / `-S` 判定每个可疑点是上游带来还是本 fork 既有。
- **真机实测**：在设备上直接触发错误场景，看模型实际收到什么（本文档最有价值的部分）。

**已知盲区（务必记住）**：动态注入的 schema 静态正则抓不到。首轮误报 11 个"僵尸"，
逐个核查后 10 个是假阳性：

| 误报 | 真实注册路径 |
|---|---|
| `search_bills` 等 8 个 | `AgentPersonalSearchToolCatalog` 按 `PersonalSearchTools.searches.forEach` 生成 |
| `set_flashlight` 等 23 个 | `AgentDeviceToolCatalog:14` 转注册 `AgentPhoneToolCatalog` |
| `character_memory_get/write` | `AgentRuntimeRunExecutor:230` 角色会话才 `appendSchemas` |

## 二、发现分类

| 类别 | 结论 | 处置 |
|---|---|---|
| **A 僵尸工具** | 仅 `run_command`：`42b9930` 删了它的 schema 注册，执行侧/要求表/显示映射仍在 → **永不自愈**失败 | v3.8.1 加迁移引导 |
| **B 半死兼容** | `action=open_and_exec`、`environment=alpine/debian` | **误判，已回滚**（见第三节） |
| **C 结构型限制** | `oneOf`/`anyOf` 报错把「0 分支匹配」与「超上限」折叠、且不指字段 | v3.8.1 初修、v3.8.2 深化 |
| **D 记忆污染** | 长期记忆里 `open_and_exec`×3、`run_command`×4 仍按旧用法书写 | 写入《terminal 调用现行规则》（注入区） |

**能力投影本身是对的**：`AgentToolCapabilities.project` 对不可用工具直接不放进目录，
`nfc`/`night_light` 不可用时还会收窄 enum —— 所以 root/无障碍/开关类"限制"模型根本看不到，
不会踩。

## 三、一次误判与纠正（留痕）

审查中一度把 **「能力目录拒绝 / 运行时接受」** 判为"上游漏同步 schema"，并**已动手修改**
`TerminalToolContract`（把 `open_and_exec` 补进 actions 表、把 `alpine/debian` 补进 enum）。
跑测试时被两处拦下：

- `RootShellTerminalControllerTest:205-207`：`assertNotNull(validator.validate(...))` +
  `assertNull(TerminalToolContract.validate(...))` —— 明确断言这**是有意分层**：
  能力目录只暴露规范写法引导模型，运行时保留旧名容错；
- `AgentToolCatalogTest`：断言 `enum` 恰为 `[android, linux]`（`linux` 是抽象值，
  按用户设置落到具体发行版）；
- 另发现该测试文件内**另有 4 处直接以 `open_and_exec` 调用 controller** ——
  说明运行时兼容是被测试依赖的，若按"删兼容"方案会全线崩。

**处置**：两处 schema 改动全部回滚（`TerminalToolContract.kt` 最终回到 HEAD 状态），
并新建 `TerminalToolContractTest` 把该分层**显式锁住**，防止将来被"顺手统一"。

## 四、真机实测发现的 4 个缺口（v3.8.2 修复）

v3.8.1 上线后在设备上试了两个真实错误：

1. `terminal` + `action=open_and_exec` → 「……分支1：arguments 符合了 not 禁止的 Schema；
   分支2：arguments.action 不在允许值集合中；分支3：…」
2. `daemon_logs` + `environment` → 「……分支1/2/3：arguments 符合了 not 禁止的 Schema」（三条一样）

| 缺口 | 修复 |
|---|---|
| 分支只报编号（`分支2` 是哪个 action？） | 从分支单一枚举字段推出标签：`action=exec：…` |
| `not` 不说是哪个字段多余 | `含当前 action 不接受的字段：environment（请移除后重试）` |
| 只列前 3 条、看不到全集 | 附 `「action」的合法取值：open、exec、…、daemon_stop` |
| 截断无提示 | `（共 8 个分支，仅列前 3 个）` |

无法归因的形态一律回退原文案（`fetch_url` 的纯 `required` oneOf 已验证仍清晰）。

## 五、遗留项

1. **`run_command` 引导无法真机实测**：该名不在工具定义里，模型无法主动构造该调用，
   只能用单测覆盖（`retiredToolNameGetsMigrationGuidanceInsteadOfGenericMissingTool`）。
2. **记忆 366/383/470 行的历史提法保留原貌**：属档案记录且不在注入区，由《现行规则》覆盖。
3. **`ShellFileToolBackendTest` 偶发 flaky**：`runShell()` 读 `process.inputStream` 前
   未等进程结束（管道时序），CI 上偶发 `java.io.IOException`（非断言失败，本地 2/2 通过）。
   属上游测试代码，建议后续单独处理。
