# v3.8.7 — 熔断后的裁剪兜底（R6）

小修复：补上 v3.8.6 引入熔断时留下的那个空档。

## 背景

v3.8.6 把压缩触发线降到 `min(窗口 × 0.75, 20 万)`，并让压缩失败后熔断（本 run 内不再重试）。
但熔断只挡住了「重复压缩」，没挡住「重复超线请求」：压缩失败后每轮仍把整份上下文发出去，
直到估算顶到窗口才被硬裁剪 —— 在 100 万窗口上，压缩线与裁剪线之间的空档从 17.6 万变成 **72.6 万**。

## 修复

- `AgentContextSession.compactionBlockedForRun`：把熔断状态暴露给调用方。
- `AgentLoop`：熔断后把硬裁剪线从 `config.contextWindow` 降到
  `AgentContextBudget.triggerTokens(window)`（= `min(0.75 × 窗口, 20 万)`），
  即压缩失败的同一轮就地把出站请求裁到触发线量级。

未熔断时逻辑完全不变（仍只在接近窗口时裁），因此不影响 v3.4.0 审查 C1 确立的
「新鲜 run 不得被过度裁剪」——那条测试（`freshRunWithOversizedHistoryTrimsRound1BeforeSending`）保持通过。

## 测试

- 新增 `AgentContextCostGuardTest.failedCompactionFallsBackToTrimAtTriggerLine`：
  窗口 90 万 / 触发线 20 万 / 历史约 78 万，首轮摘要失败后断言第二轮出站请求估算 < 30 万，且出现 `HistoryTrimmed` 事件。
- 本地相关用例全绿：`AgentContextCostGuardTest` 5、`AgentContextCompactionTest` 17、`AgentContextRecoveryTest` 14。
  （本机 aarch64 上 Robolectric 用例仍因 `DefaultNativeRuntimeLoader` 环境性失败，以 CI 为准。）

## 行为变化

仅在「摘要压缩已熔断」这一异常路径下更早丢弃旧历史；**只影响出站请求，不改持久记录**，
用户侧会话记录不会因此丢失。
