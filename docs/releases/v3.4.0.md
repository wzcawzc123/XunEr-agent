## Eta v3.4.0

本版修复一个会导致**超大图片附件整张丢失**的产品缺陷，并补上两处让它一直没被发现的测试前提。

### 修复：超大用户附件不再整张丢失

`AgentModelImageEncoder.userAttachment()` 复用了 `toolVisionProfile`，而该档位既没有 `maxLongEdge`
也没有 `maxPixels`，使得 `targetSize()` 里的 `scale` 恒为 1.0 —— 它与文档承诺的"按需采样解码到
1600px"从未生效。于是 13–40MiB 的相机原图会被按**原尺寸** JPEG(quality 95) 重编码；一旦结果超过
`MAX_AGENT_IMAGE_BYTES`(12MiB)，`encodeBitmap` 中的 `require` 抛错，又被外层
`runCatching{}.getOrNull()` 吞掉 —— **整张附件静默消失**，而不是被降级救回。

- **修复**：新增 `userAttachmentProfile`（长边 1600 / 150 万像素）供用户附件使用。
  `toolVisionProfile` 保持原样，以免破坏"文件工具图片保持原尺寸（3200×2400）"的既有回归断言。
- **影响**：相机 / 相册里的超大原图现在会被正常降级后发出，不再整张丢失。
- **未改动**：普通附件、截图、文件工具图片的编码路径。

### 测试：补上两处"让缺陷隐身"的前提

- `AgentImageCodecTest.patternedNoiseBitmap` 原本用 4×4 色块构造"不可压缩的噪声图"，
  但块内上下行完全相同，PNG 的行滤波会把它们整片压掉 —— 3000×2000 只产出 1,635,071 字节
  （约原始的 1/16），"前置条件：噪声 PNG 应超过 12MiB"这条断言先失败，
  上面那条降级路径**事实上从未被执行到**。改为逐像素随机后为 20,662,942 字节。
- `BreenoRequestImagesTest.inlineImageIsNoLongerRejectedByBinderStringBudget` 的输入是
  `"A".repeat(300_000)`，并不是图片；自 `c15de97`「统一内联图片编码路径」起，`data:` URL
  必须能解出真实图片才返回 `Success`，因此该用例注定失败，与产品行为无关。
  改为真实的 900×700 噪声 PNG，并显式断言 base64 长度 > 1MiB，以保留"超过旧 Binder 字符串预算"的原意。
