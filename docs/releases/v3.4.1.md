## Eta v3.4.1

本版处理「工具调用参数丢失」这一族报告：先用真机抓取把归因定死，再修掉三条独立缺陷。

### 背景：harness 不会丢参数（真机抓取结论）

报告最初是三条现象 —— `memory_get` 的三个参数"被忽略"、`terminal` 的 `environment=linux`
"被系统性剥离"、`memory_write` 的必填字段"轮换缺失"。为切开"模型没发"与"链路丢了"，
把 provider 的 base_url 临时指向本机透明代理（`adb reverse` 走 USB，不经局域网），
**逐块录制模型的原始 SSE**，再与 harness 回传给模型的内容逐字符比对：

- **4 个并行调用**（参数均为 `{}`）：原始 SSE 与回传**逐字符一致**
- **`memory_write` 的 21 个碎片**（token 级流式，最小 1 字符）累积出的长参数：**一字未改**，写入成功
- **强制模型省略必填字段 `revision`**：SSE 里确实没有 → harness 原样透传 →
  工具如实返回 `INVALID_TOOL_ARGUMENTS · arguments 缺少必填字段 revision`
- **`environment=linux`**：SSE 里有 → 回传一致 → **实际执行在 Debian 13**
  （结果 `"environment":"debian"`、`stdout` 为 `PRETTY_NAME="Debian GNU/Linux 13 (trixie)"`）

⇒ **参数到达与透传都没有问题；"丢失"来自模型侧漏发。** 而它之所以会被误判成 harness bug，
正是因为下面 ① 的静默兜底让两种情形在观测上无法区分 —— 当时连模型自己的推理都写下了
"environment 被系统性剥离，本会话存在 harness bug"，并因此放弃重试、绕道手搓 zip。

另外两处顺带澄清：`memory_get` 不带参数时**默认就返回 `start_line=1 / end_line=63 / has_more=true`**
（12000 字符一页），所谓"恒为第 1-63 行"是默认分页行为本身；`terminal` 的结果摘要里不含 `environment`，
但**原始工具结果里是有的**（被省略的是持久化摘要）。

### ① `terminal` 的 `environment` 不再静默兜底

`AgentLocalTools.terminal()` 原先用 `args.optString("environment", "android")`：取不到就**静默**变成
android，既不报错也不回显 —— 把"模型没传"伪装成了"参数正常"。现在：

- 非空但不可识别 → 明确返回 `INVALID_TOOL_ARGUMENTS`
- 缺失 → 仍按 android 执行，但结果里加 `environment_source="default"` 与一句说明
- **显式传参的路径行为完全不变**（只新增字段，不改原有字段）

### ② 校验失败自带证据

`AgentToolCallValidator` 原先只报第一个缺失字段（`缺少必填字段 revision`），无法区分
"模型压根没生成该字段"与"链路把参数丢/串了"。现在一次列全所有缺失字段，并附上实际收到的字段清单与
**形状**：

```
arguments 缺少必填字段 revision；已收到字段：mode(str:6)、content(str:951)
```

只输出键名与各值的类型/长度，**不输出取值**（错误信息里不落内容）；空对象时回显 `已收到字段：（无）`。

### ③ 脱敏不再让模型"失忆"

`AgentConversationCodec.transcript()` 原先把敏感工具的参数与结果整块替换成
`{"redacted":true}` 与一句省略文案，结果模型**看不到自己上一轮调了什么、也看不到返回了什么形状**，
只能反复重试 —— 实测同一会话里出现 **34 次完全相同的 `memory_get`**、另一会话 **1,283 次 `terminal`**。

现在改为保留"形状"：保留 `_redacted` 标记与原有省略文案，并给出各字段的类型/长度
（白名单键如 `ok` / `code` / `count` / `has_more` / `exit_code` 保留原值，仅限布尔、数字与 ≤64 字符的短字符串）。
取值一律不留 —— 既有回归测试里"不得出现 `敏感值` / `secret-value`"的断言继续成立。

### ④ `search_downloads` 修正数据源

原先用 DownloadManager 的 `content://downloads/my_downloads`，却配了 MediaStore 的列名
（`mime_type` / `lastmod`）。真机 `content query` 直接复现 `Invalid column mime_type`，
该错误被兜底成 `PERSONAL_DATA_UNAVAILABLE`，表现为"下载目录永远查不到"
（真机实测该目录有 **110** 个文件；用合法列名查同一个源则返回 0 行 —— 说明它本就只包含
本应用自己发起的下载）。现改用 `content://media/external/downloads` + MediaStore 列名
（`_display_name` / `mime_type` / `relative_path` / `date_modified` / `_size`），
与本文件里其它工具保持一致，并补上 `uri` 字段。

### ⑤ 备份导出改为流式

`EtaBackupRepository.export()` 原先 `encodeToString(...).toByteArray()` 一次性物化整份内容，
峰值约为备份体积的 2~3 倍（String + byte[]，再加 `prettyPrint`）—— 实测在约 218 MB 的数据集上直接
`OutOfMemoryError`（`Failed to allocate a 228271720 byte allocation with 25165824 free bytes`）；
而且 64 MiB 上限检查发生在分配**之后**，那句友好报错永远不可达。现改为流式 `encodeToStream`
配合写入量上限保护：内存占用降到近似常量，超限时立刻抛出可读错误。

### 版本号

`versionName` `3.4.0` → `3.4.1`，`versionCode` `2026100101` → `2026100201`。

### 验证

- **Windows 11 / JDK 25 / SDK 37**：1139 项，通过 1101，失败 36，跳过 2。
  与基线做**用例级集合差集**：**新增失败 0 条（无回归）**。
- **WSL2 / Ubuntu + JDK 25**：1139 项，**通过 1135，失败 2，跳过 2**。
  剩余 2 项为 `DexKitNativeLibraryFileTest` 在 root 身份下的权限位假失败（以普通用户运行即通过，非代码问题）。
- Windows 侧那 36 项**全部**是"Windows 作为测试宿主"的平台差异
  （pty / root shell / 盘符冒号 / 记忆文件存储等），**在 Linux 上均通过**，非产品缺陷。
- 新增/修改的针对性测试：`AgentToolCallValidatorTest#missingRequiredFieldsReportWhatWasActuallyReceived`，
  以及 `AgentSensitiveTranscriptTest` 新增 4 条断言（同时锁住"形状保留"与"取值不泄露"）。

> 未改动（有意保留）：备份的 `prettyPrint` 与图片 data URL 的排除策略 —— 会改变备份文件格式，
> 风险高于收益；流式化之后内存已不是瓶颈。
