# v3.11.3 — 修复本地估算高估导致的误裁剪

小修复，但是**实质性**的一个：修掉"看起来在压缩、实际在丢数据"的问题。

## 问题（真机取证，会话「性能调度模块-新会话」）

| 项 | 值 |
|---|---|
| 本地估算 `rawEstimate` | 1,377,249 |
| 服务端实测 `input_tokens` | 285,683 |
| **估算 / 实测** | **4.82 倍** |

**后果**：硬裁剪判据是"估算 ≥ 窗口（100 万）"—— 实测仅 **28.5 万**时就判定"已超窗口"，
于是走 `AgentHistoryTrimmer` **纯丢弃最旧消息**（不生成摘要、没有锚点、没有八小节）。

**两个可观测症状互相印证**：

- 摘要字符数与数日前**一字不差**（4,486）→ 它压根没被重新生成
- 摘要内容停在完整历史 **44%** 位置 → 它仍是第一次真摘要的产物

也就是说：用户看到的"第二次压缩（降幅 63%）"实际是**硬裁剪**。

## 根因（两层）

1. **设计好的校准机制从未接上**：`AgentContextBudget` 提供 `observe` / `estimate`（用实测校准估算），
   但**生产代码从未实例化它**（只有测试引用），`AgentLoop` 直接用未校准的静态 `rawEstimate`。
2. **即便接上也修不了**：其校准值 `coerceIn(1.0, 8.0)` **结构性禁止向下修正**，
   而本例恰恰需要 1 / 4.82 = 0.207。

## 修复

1. **激活校准**：`AgentContextSession` 持有 `AgentContextBudget`；`AgentLoop` 每轮收到 usage 后喂入实测，
   并用**校准后的估算**做裁剪判据。
2. **校准改为双向**：下限 0.1、上限 8.0 —— 高估与低估都必须能纠正。
3. **保持不变式**：裁剪后的复核**重新估算**（不复用裁剪前的值）；`systemEstimate` 与判据同口径。

**关于中文折算系数**：曾一并把非 ASCII 从 1 字符/token 改为 1.5 字符/token，但**已回滚**——
校准的数学是 `判据 = 估算 × (实测 / 估算) = 实测`，**无论估算尺度如何，校准后都精确等于实测**，
系数修正对判据准确性零贡献，却会破坏既有的尺度契约（8 个用例依赖旧口径）。故不做。

## 修复效果（同一份真实数据）

| | 判据值 | 对照裁剪线 100 万 |
|---|---|---|
| 修复前 | 1,377,249 | ⚠️ 误触发硬裁剪 |
| 修复后 | **285,683** | ✅ 不触发（精确等于实测） |

## 验证

- 新增 4 个用例：估算高估时向下修正、未观测时不改变估算、非法值不影响校准、英文折算保持不变。
- 全量 **1630** 用例，失败 356 = **354 环境性**（aarch64 Robolectric）+ **2 既有**（root 下 `canWrite`），
  与改动前基线逐项一致。
- 影响面：**仅本地估算与裁剪判据**；发送给模型的上下文内容不变（修剪与压缩逻辑未动）。

## 备注

- 首轮（尚无任何实测）仍使用纯估算；从第二轮起校准生效。
- 校准由服务端 usage 驱动，换模型后首轮重新建立。
