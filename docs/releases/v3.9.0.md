# v3.9.0 — 压缩策略对齐 DeepSeek Harness：80% 触发 + 逐字保留 + 需求锚点

功能迭代：把上下文压缩从「尽早压、压到极小」改为「晚压、压得狠、保住关键」。

## 背景

v3.8.6 / v3.8.7 把触发线压到 20 万，成本可控但带来两个副作用：

- 压缩频率升高（压完常驻仅 6~7 万，涨 14 万就再压），**多代摘要的漂移风险上升**；
- 用户可用的连贯上下文显著变短。

本次按需求改为 **80% 窗口触发**，并按 deepseek-ai/deepseek-harness（MIT）的口径补齐三处配套，
让「晚压」不至于变成「又贵又记不住」。

## 改动

1. **阈值公式对齐 harness**：`trigger = min(floor(W × 0.8), W − 输出预留 − 余量)`
   - 输出预留 16,384、余量 65,536（与 harness 默认一致）；小窗口下按 `W/16`、`W/8` 收缩
     （harness 在小窗口直接报配置错误，Eta 允许任意窗口，故按比例退化）。
   - 100 万窗口：**触发线 ≈ 838,860**（v3.8.7 为 20 万封顶，v3.8.6 之前为 750,000）。
   - 顺带修掉旧公式漏算「输出预留」的缺口。
2. **逐字保留尾部**：`retain = (W − 输出预留) × 0.16`（100 万窗口 ≈ 16.5 万）。
   压缩后常驻从 6~7 万提升到 ≈ 20 万，一次压缩可管 60 万以上增长 ——
   **压缩次数、缓存击穿次数与摘要代数同时下降**。
3. **需求锚点**：会话首条用户消息逐字带过每一代摘要（标记 `[原始任务（逐字保留，勿改写）]`），
   直接对症「多次压缩后模型对我的真实需求越来越模糊」。
4. **结构化摘要**：固定 8 小节（原始需求与意图 / 关键技术概念 / 文件与代码 / 错误与修复 /
   待办事项 / 当前工作 / 下一步 / 关键上下文），并要求「保留仍成立的事实、丢弃过期信息、
   把新信息合并进同一结构」（参考 harness 的压缩指令）。

## 测试

- `AgentContextCostGuardTest` 增至 **6 例**：新增阈值与保留预算公式断言、
  `compactionCarriesVerbatimAnchorAndKeepsRecentTail`（锚点逐字 + 近期尾部保留 + 显著缩减）。
- 相关类全绿：CostGuard 6、Compaction 17、Recovery 14。
- 本机 aarch64 上 Robolectric 用例仍为环境性失败（20 例，与基线一致），以 CI 为准。

## 代价（请知悉）

每轮输入可能增长到 80 万量级 —— 按「命中 ≈ 1/10 价」折算，**等效成本约为 20 万档的 4 倍**；
换来的是压缩次数大幅减少、需求不漂移、近期上下文逐字在场。

如需回到省钱档，把 `AgentContextBudget.ABSOLUTE_TRIGGER_CAP` 设为 `200_000` 即可
（0 = 不设上限，即当前 80% 行为）。后续可做成可配置项。
