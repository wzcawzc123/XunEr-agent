# v3.11.24 — 稳定性体检批次 A：高危五项修复（上下文裁剪/会话数据守卫/编辑重发守卫/OCR index）

## 背景

对当前版本做 3 域并行只读体检（上下文压缩、会话恢复、GUI/OCR 工具层），
发现高危 5 项、中危 9 项、低危若干。本版为**批次 A：高危 5 项全部修复**；
中危批次 B 与低危顺手项留待下版。

## 根因与修复

### H1 — 签名回合内硬裁剪无守卫，瞬态键被裁剪剥掉
- **根因**：压缩路径有 Anthropic 签名守卫（`ANTHROPIC_THINKING_CONTEXT_LOCKED`），
  但**硬裁剪路径没有对等守卫**；且裁剪经 `fromJsonObject→toJsonObject` 全量重建，
  剥掉 `_eta_anthropic_content_blocks`（思考签名）、`_eta_observation`、`_eta_assistant_screen_context`
  三类瞬态键——签名轮被裁剪后，上游判定"改动了 thinking 块"，同一会话后续每轮 400。
- **修复**：`AgentLoop` 裁剪块加 `hasPendingToolResponse` 守卫（与 compact 对等，延后裁剪）；
  `AgentHistoryTrimmer` 新增 `trimJson`（直接操作原始 JSONObject，保留全部 `_eta_*` 键），
  旧 `trim(ConversationMessage)` 委托给 `trimJson` 保持既有测试契约。

### H2 — 硬裁剪目标与判据单位混用（校准口径 vs raw 口径）
- **根因**：`AgentLoop` gate/afterTrim 用校准后估算（`budgetEstimate`），
  而 `AgentHistoryTrimmer` 内部 `costs`/`EMPTY_ESTIMATE`/`TOOL_SCHEMA_RESERVE` 全是 raw 未校准；
  同一公式混用两种单位。cal<1（常态，真机 0.2~0.7）时每次硬裁比设计多丢 1.7~4 倍历史；
  cal>1（上限 8.0）时裁剪成功后 `afterTrim = cal×raw ≥ window`，`CONTEXT_EXHAUSTED` 安全网 100% 失效。
- **修复**：`AgentContextBudget` 暴露 `calibrationValue()`；`AgentHistoryTrimmer.trimJson` 增加
  `calibration` 参数，内部成本统一乘校准换算到窗口单位后与 `limit` 比较（Double 累计避免截断误差）。
- **验证**：新增 cal=0.25 / cal=2.0 两档回归测试（现测试全部在 cal≈1 附近，恰好绕开缺陷）。

### H3 — 懒加载失败被永久标记"已载入空态"，后续写库可清空整会话
- **根因**：`lazyLoadConversation` 失败分支把占位置 `messagesLoaded=true` + 空 messages；
  之后 `saveChanges` 以空基线做 diff → `deleteMessagesFrom(id,0)` 清空库内全部消息、
  checkpoint 也被空 history/journal 覆盖——**"会话切换空白页、重后台后复发"的残留根因**。
- **修复**：失败时**不再**置 `messagesLoaded=true`（保持 false，下次切换/选中会重试），
  新增 `conversationLoadFailed` 标记供 UI 呈现；`AgentConversationStore.saveChanges` 双保险：
  未载入（`!messagesLoaded`）或"全空占位 + 旧基线非空"的污染态一律跳过 checkpoint 与消息区写入
  （用户手动删光消息时 history/journal 仍非空，不会误命中）。
- **验证**：新增 `pollutedEmptyLoadedStateDoesNotWipeStoredMessages`（库内消息必须保留）。

### H4 — 编辑重发容量守卫配置源可能整体失效 / 与实际运行窗口错位
- **根因**：守卫读 `AgentModelClient.loadConfig().contextWindow`，而 `loadConfig()` 走
  `Prefs.getString`（remote/Xposed 未连接时返回空串）→ 落到默认配置 `window=null` →
  **守卫整段静默跳过**；即使读到值也是默认模型窗口，与 run 实际用的
  `runtimeConfigFor(runModelId)`（会话绑定模型）可能错位。
- **修复**：守卫窗口改为与 run 同源——优先取**会话绑定模型**的 `effectiveContextWindow`
  （`providers.enabledModel` 纯函数同步可读），回退 `loadConfig()`，再回退保守默认 128k（不再跳过）；
  阈值留 5% 余量（`≥ window×0.95`），`guardOverhead` 保底 `TOOL_SCHEMA_RESERVE_TOKENS`（防归零）。

### H5 — OCR 分支 index 与 UI 节点 index 两套编号，tap_element 可能静默点错
- **根因**：`locate_on_screen` OCR 源返回的 `node_index` 是**识别块序号**，但发布的是树快照的
  `observation_id`，schema 引导用 index 调 `tap_element` → 序号落在树节点范围内时**命中的是另一个节点**。
- **修复**：OCR 源 `node_index` 恒置 `-1`（不可用于 tap_element）+ note 明确"用 center_x/center_y +
  coordinate_space=screen 调 tap"；`tap_element`/`longPressElement` 对 `index<0` 直接拒绝
  （`INVALID_NODE_INDEX`，附修正引导）；两处 schema 描述同步限定（index 仅 ui_tree 源可用）。
- **验证**：更新 OCR 测试断言（`node_index == -1`）+ 新增 `tapElementRejectsOcrSourceNodeIndex`。
