## Eta v3.4.4

本版集中处理「上下文快速膨胀 → 触发压缩 → Runtime 运行失败 / 已停止」这一连锁问题。
经过真机日志抓取、数据库副本分析与构造性单元测试，已定位并修复全部直接真因。

### 一、问题真因

用户反馈：点击、界面树、截图等动作执行几次后，很快就会提示"上下文已压缩"，
随后任务以 `Runtime 运行失败 / 已停止` 告终。

最终确认这是**两条线叠加**的结果：

1. **直接失败原因：HTTP 402（余额/额度不足）**
   - 真机日志里出现 `model_code=HTTP_402`。
   - 原错误提示只显示状态码，用户无法判断是欠费，于是误判为压缩本身导致崩溃。

2. **深层诱因：history 是完整会话累积，不是压缩摘要**
   - 数据库副本显示，未压缩过的会话中 `history_json` 与 `journal_json` 逐字节相同。
   - 说明 `history` 就是完整 transcript，会一路累积到触发压缩线。
   - 在 100 万窗口下，85% 触发线 = 850,000 tokens，实测 `before=854,005` 触发压缩。

### 二、修复内容

#### ① HTTP 402 提示明确化

`AgentModelFailure.kt`：将 402 判定为不可重试，并给出明确提示：

> 模型接口余额或额度不足（HTTP 402），请到服务商账户充值，或更换可用的 API Key。

#### ② history 有界兜底

`AgentConversationStore.toLegacyHistory()` 现在对 legacy history 做硬边界：

- 最多保留 **40 条**消息；
- 字符总量不超过 **32,000**；
- 从最新消息往回取，保证"当前在做什么"不会丢。

常量：`LEGACY_HISTORY_MAX_MESSAGES = 40`、`LEGACY_HISTORY_MAX_CHARS = 32_000`。

#### ③ AgentHistoryTrimmer 硬上限保护（新建）

新增 `AgentHistoryTrimmer.kt`，在 `AgentLoop` 真正发送模型请求前做最后一道保险：

- 从最新消息往回删；
- 保证 `systemEstimate + historyCost <= contextWindow`；
- 预算不足时返回空历史，而不是发出必然失败的请求。

接入点经过调整：最初放在 `AgentPromptBuilder.buildInitialMessages` 里，但会导致
`AgentContextSession.compact()` 无法感知大历史、从而不触发智能摘要压缩。现移到
`AgentLoop` 请求发送前，先让压缩机制工作，若仍超窗再做硬裁剪。

#### ④ 续跑路径同步加固

`AgentContinuationBuilder` 在构造续跑请求时，现在会对生成的 `baseHistory` 也做一次
`AgentHistoryTrimmer` 兜底裁剪。防止"继续执行"或气泡补充时把超大历史带进下一 run。

#### ⑤ 压缩触发线从 85% 降至 75%

`AgentContextBudget.TRIGGER_RATIO`：`0.85` → `0.75`。

- 100 万窗口下，触发线从 850,000 降到 750,000；
- 为系统提示、工具 schema 和本轮增长留出 25% 安全余量；
- 减少"压缩后仍逼近窗口"的情况。

### 三、验证

- **WSL / Linux 全量单元测试**：1173 项，通过 1169，失败 2，跳过 2。
- 剩余 2 个失败为 `DexKitNativeLibraryFileTest`，与 Android native 库 ABI 有关，属 WSL 环境限制，
  与本次改动无关。
- 相关改动测试全部通过：
  - `AgentContextCompactionTest` ✅
  - `AgentContinuationBuilderTest` ✅
  - `AgentHistoryTrimmerTest` ✅
  - `AgentModelRetryTest`（新增 402 断言）✅
  - `LegacyHistoryBoundsTest` ✅

### 四、已知限制与后续方向

- 压缩摘要质量仍依赖模型生成的摘要；后续可考虑在摘要中保留高优先级约束。
- 工具 schema 固定占用约 15,000 tokens；后续可按会话主题动态选择可用工具子集。
- 截图、界面树等大内容仍是历史膨胀主力；后续可对老截图/旧界面树做降级存储。
