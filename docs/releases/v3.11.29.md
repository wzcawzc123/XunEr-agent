# v3.11.29 — 上下文压缩判据修正（字符数判定 / 保留预算 / 实测基准）

## 背景

真机反馈（2026-10-16，会话「个人简历」）：手动压缩后提示条显示
「摘要只把上下文从约 **420083** 降到 **412433** tokens」（仅降 1.8%），
而模型随后反馈「上下文已用到 99%」，用户认为压缩失效。

核查确认：**压缩实际非常有效**（实测 `input_tokens` **777,273 → 365,278**，↓53%），
**失效的是判据**。完整审查见 `docs/reviews/context-compaction-audit.md`。

## 根因

`rawEstimate` 按「ASCII 3 字符 = 1 token」估算，对**工具结果（JSON）系统性低估约 1.85 倍**
（真机：估算 420,083 vs 实测 777,273）；而压缩后历史以摘要文本为主时估算反而准确
（估算 363,922 vs 实测 365,278，偏差 **0.4%**）。

两者相比得出的「降幅」完全失真：

```
估算降幅 1.8%   →  判定「不划算」→  摘要被拒
真实降幅 53%    →  本应通过
```

摘要被拒后退化为**硬裁剪**（纯丢弃），用户感知为「压缩无效 + 失忆」。

**这也是此前多次修复未解决的原因**：每次只调整了同一条失真判据的一环。

## 修复

1. **降幅判定改用字符数**（`AgentContextCompactor`）
   字符数与 token 数在同一次比较中方向必然一致，不受内容成分影响。

2. **压后超线判定改用字符比例缩放**（同文件）
   原式用「压缩后的 rawEstimate × 为工具密集场景标定的 calibration」，
   对以摘要文本为主的压缩后内容会高估。

3. **`compactEnd` 保留成本不再乘 calibration**（同文件）
   压缩发生时 calibration 往往仍是初值 0.4（来自「估算高估 4.82 倍」的时代），
   与当前「低估」方向相反 → 成本被缩小 2.5 倍 → 保留量超预算约 1.8 倍
   （实测：预算允许 256 条，实际保留 454 条 / 634K 字符）。

4. **校准初值改为中性 1.0**（`AgentContextBudget`）
   原 0.4 隐含「估算必然高估」的假设；工具结果密集场景实测 1.85，方向恰好相反。

5. **压后超线判定改用实测 input tokens 作基准**（`AgentContextCompactor`）
   与真实请求同口径，同时消除「估算分母含/不含 tools」的口径不一致。

6. **提示文案按原因分流**（`AgentEvent`）
   `CONTEXT_NO_REDUCTION` 属主动取舍（原文仍在使用），不再显示为「压缩失败」。

## 效果（同一份真机数据推算）

|---|---|---|
