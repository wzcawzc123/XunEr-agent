# v3.11.30 — 模型不再臆测上下文用量（约束 + 压缩时如实告知）

## 背景

真机反馈（2026-10-16，会话「个人简历」）：

界面显示用量 **36.9%**（实测 365,278 / 1M），而模型称：

> 「我要跟你说实话：**这个对话的上下文已经用到 99% 了**，我剩下的空间只够写一条回复…」
> 「刚才那条已经把它推到 **99% 以上**了，我现在的余量只够短回复」

**核查确认模型并无该数据来源**：

- **系统提示不注入用量** —— Eta 仅在 UI 层计算 `contextUsage`，从未传给模型
- **摘要文本中亦无用量字样** —— 已核对 3,883 字符的摘要全文，零命中

即：模型是从「对话很长」推断出一个偏高数字，**误导用户以为容量将尽**。

## 修复（两个互补方案）

### ① 明确告知「没有该数据来源」，禁止断言用量

主系统提示新增（固定文案，不随轮次变化）：

> 你无法感知当前上下文的占用百分比，也没有该数据的来源；
> 不要断言「已用到 X%」「余量只够…」「快满了」这类用量判断。
> 用户问及时，说明应以界面显示的用量为准；必要时可提示对方手动压缩历史。

**作用**：模型不再编造数字。

### ② 压缩完成时，把实测占用写入摘要一次

在摘要的「原始任务锚点」之后追加：

```
[压缩时的上下文占用：约 77%（实测 777273 / 1000000 tokens）。
 该值是压缩【前】的实测，压缩后的实际占用显著更低；
 后续请以此为准，不要凭对话长度推测用量。]
```

**作用**：模型不仅能知道真实量级，还知道"压缩后会更低"，可据此合理规划后续步骤。

## 关键设计取舍（为何不做逐轮注入）

**方案 ② 没有采用「每轮注入当前用量」**，原因是它会破坏 prompt 缓存：

```
系统提示逐轮变化
    ↓
prompt cache 逐轮击穿
    ↓
代码注释记录的同类代价：「命中率 99.9% → 9.4%，等于全价重算」
```

**为了一句「当前用量 X%」而让每一轮按全价计费，得不偿失。**

改为「只在压缩完成时写入一次」，同时获得两个好处：

| | 效果 |
|---|---|
| 不随轮次变化 | ✅ **不影响缓存命中** |
| 时机精准 | ✅ **压缩后正是模型最需要知道余量的时刻**（刚经历摘要，需据此规划后续）|
